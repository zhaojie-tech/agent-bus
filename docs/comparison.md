# 生态位对比（为什么是 agent-bus）

## vs. 临时文件 / 共享剪贴板 / 约定文件名

多实例协作的最低配方案：往 `/tmp/xxx.md` 写文件、让另一个 agent「去看看
那个文件」。

| 维度 | 临时文件 | agent-bus |
|---|---|---|
| 寻址 | 路径靠口口相传，易漂移 | 实例编号 `codex#1`，发现守护自动登记 |
| 可见性 | 谁都能读，无成员概念 | 可见性=room 成员关系，非成员 `E_NOT_MEMBER` |
| 投递 | 对端不知道有新内容（靠人催或轮询） | per-member 投递状态 + 30min 重投 + 终端提醒 |
| 归属与审计 | 散落无主，谁改的说不清 | 消息/任务全量入库，human `room show --history` 全程可审计 |
| 并发 | 覆盖写互相踩 | 乐观锁 + 单事务裁决 |
| 生命周期 | 忘了删就是垃圾 | closed 三阶段自动归档 |

一句话：临时文件是**无纪律的共享**，agent-bus 是**带投递语义和审计线的
通信**。

## vs. 重型消息队列（Redis/RabbitMQ/NATS…）

MQ 是为跨网络、跨语言、高吞吐的分布式系统设计的。本机多 AI 实例场景里
它们带来的问题比解决的多：

- **运维成本**：要装一个常驻服务（Docker/系统服务），agent-bus 是一个
  SQLite 文件，`pipx install` 即用，离线机器可装。
- **语义错位**：MQ 的 at-least-once/at-most-once、消费者组、ack 批量
  语义面向吞吐；这里需要的是「每个成员独立已读、30 分钟不确认就重投、
  room 关闭后归档」这类**协作纪律**语义，拿 MQ 还得自己搭一层。
- **审计错位**：MQ 的可观测性面向吞吐与积压；这里的审计对象是
  「哪个 agent 在哪个 room 说了什么、任务谁认领的、human 什么时候批的」。
- **依赖纪律**：agent-bus 零运行时依赖（ADR-0003）；引入 MQ 即放弃该特性。

MQ 的真正出场时机是 v0.3 的跨主机 relay（可插拔传输层）——那时才存在
「网络」这个 MQ 擅长的维度。

## vs. agent 框架自带消息层（LangGraph/AutoGen/CrewAI 等）

框架的消息层解决「**同一个程序里**的多 agent 编排」：同一进程/同一运行时
内的 agent 间通信，框架负责调度智能。

agent-bus 解决的是互补的另一面：「**同一台机器上、彼此独立的交互式
实例**」（不同的 CLI、不同框架、甚至不同厂商的模型，各开各的终端）之间
的通信与协作纪律。

| 维度 | 框架消息层 | agent-bus |
|---|---|---|
| 参与者 | 框架运行时内的 agent 对象 | 操作系统里的交互式进程（claude/codex/hermes CLI…） |
| 编排智能 | 框架做调度/路由/反思 | **不做**——只做通信与协作纪律的地基 |
| 人类角色 | 框架回调里可插 | 一等公民：human 超集成员、任务 done 唯一终审入口、全程可见 |
| 捆绑 | 用它的消息层就要用它整个框架 | 与实例用什么框架/模型无关 |
| 状态 | 框架内存/checkpoint | 本机 SQLite，人类可直接审计 |

两者可以叠用：框架管单实例内部的编排，agent-bus 管实例之间的发现、
定向通信与人类监督。
