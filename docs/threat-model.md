# 威胁模型（v0.1）

> 本文档如实陈述 agent-bus v0.1 的安全边界：它防什么、不防什么、为什么
> v0.1 不带消息签名。背景论证见 [ADR-0002](adr/ADR-0002-defer-signing.md)。

## 1. 系统模型

- 单机、单用户（同一 UID）场景。组件：`agentbus` CLI、`agentbus-discover`
  发现守护、notifier 通知器、SQLite 数据库 `~/.agent-bus/bus.db`。
- 参与者：多个交互式 AI 实例（编号 `codex#1` 等）与人类操作者（`human`，
  超集成员）。
- 信任假设：操作者本人可信；文件系统权限（0700 目录 / 同 UID）按 POSIX 语义生效。

## 2. 防什么（设计目标内）

1. **多任务混淆**：room 作用域 + 可见性=成员关系，确保实例 A 的任务消息
   不会被实例 B 误消费；非成员操作一律 `E_NOT_MEMBER`。
2. **误投递**：per-member reads 独立投递，delivered 30min 未 ack 自动重投，
   消息不因单实例卡住而丢失。
3. **越权操作**：room/任务操作在库层校验成员关系与归属；任务 done 仅
   human（人类终审门禁）；claim 乐观锁防抢占。
4. **误配置扩散**：通配成员 `kind:*` 须显式 `--wild` 才允许。

## 3. 不防什么（如实声明）

1. **sender 不可认证**：`messages.sender` 是自报字段。同一 UID 下任何能写
   bus.db 的本地进程都能伪造任意 sender、用 `AB_AS=human` 提权为超集身份、
   或直接读写数据库。总线隔离的是「多任务混淆」，**不防恶意或被攻破的
   本地进程**。
2. **`AB_AS` 误配**：`AB_AS` 是自动化编排注入身份的合法入口（无终端的
   headless worker 靠它报身份）。任何能设置环境变量的进程都能借它冒用
   任意身份——这是设计内能力，也是设计内风险。
3. **消息内容**：总线不做内容过滤。提示注入依赖协议层纪律
   （protocol-v3 §9「注入只汇报」），那是参与实例的行为约定，不是总线
   的技术强制。
4. **MCP 服务器（`agentbus-mcp`）新增三条事实**：
   - **mcpServers 配置是身份注入的新入口**——配置了 `env.AB_AS` 的 server
     即以该身份行动，与 CLI 的 `AB_AS` 同级风险；且 `AB_AS` 是静态值、
     显式优先于祖先链自动解析（有守护的环境不要设置它，详见 mcp-demo）；
   - **MCP 工具循环收窄人类可见性**——`poll_messages` 把消息正文直接注入
     模型上下文，可全程不经用户终端；trusted 档案 + MCP 构成无人类在环的
     消息→执行闭环，部署者应把此类消费纳入审计（room 历史与投递时点可回放）；
   - **编号是动态的**：实例重启后编号可能回收复用，写死在配置里的 `AB_AS`
     会指向错误实例甚至撞号——重启后核对配置。
5. **本地数据库访问**：bus.db 无加密、无访问控制（SQLite 文件权限即全部）。
6. **拒绝服务**：本地进程可随意膨胀数据库或锁表（busy_timeout 10s 兜底
   正常争用，不防滥用）。

## 4. 为什么 v0.1 没有签名层（论证复述）

直觉方案「每实例一把 HMAC 密钥，签名验证身份」在单机同 UID 场景不成立：

1. 对称密钥人人可读：任何总线参与进程都读得到 `~/.agent-bus/keys/*`
   （0600 只防其他用户）。`verified: true` 只能证明「某进程读过某文件」，
   证明不了「消息来自某个特定实例」。
2. `AB_AS` 误配反而能通过验证：按配置名误拿密钥的进程，持有的恰是
   「它的身份」对应的密钥，签名校验顺利通过——验证给了虚假的安心。
3. 消费端时效窗口（±300s 防重放）与总线异步语义互斥：delivered 30min
   超时重投是合法机制，窗口会把重投的合法消息误判为重放；而重放本就在
   §3 声明不防的范围内，窗口零收益。

结论：该密钥分发模型从未自洽。带病交付一个制造虚假安全感的签名层，
不如诚实声明边界。**v0.2 重设计方向**（per-bus 共享密钥 + 独立签名表 +
编号回收吊销 + 去时效窗口，定位「跨用户防护 + 身份卫生，不防同 UID
进程」）见 ADR-0002；签名的真实价值锚点在 v0.3 跨主机 relay——
签名随消息过网后，网络对端读不到本机密钥文件，验证才有对抗意义。

## 5. 平台边界

- 进程身份识别（祖先链 /proc 扫描、tty 回退）为 **Linux-only**；macOS 上
  身份解析降级（仅 `--as human` / `AB_AS` 显式路径可用）。
- SQLite WAL 官方明示**网络文件系统不适用**；本地盘（Linux/macOS/Windows）
  无已知语义降级。Windows 平台整体为 best-effort，未纳入支持面。
- notifier 直接写 `/dev/pts/N`（BEL）与调用 `tmux display-message`：
  均假设同 UID 权限，跨用户场景不适用。tmux 的消息参数按格式串解释，
  消息内容（含 room topic）中的 `#` 已在发送前转义为 `##`，防
  `#(...)` 命令替换面。

## 6. 给部署者的建议

- 把 agent-bus 部署在**你信任本机进程**的前提下；不信任的进程不应与
  总线同 UID 共存。
- 敏感环境可为实例使用独立 UID 隔离（代价：总线无法跨 UID 共享，等于
  每用户一条总线）。
- 订阅 v0.2 签名层进展（roadmap）：它解决的是身份卫生与跨用户防护，
  不是同 UID 恶意进程。
